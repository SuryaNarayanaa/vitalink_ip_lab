# C4 system architecture

The C4 model is defined in [Structurizr DSL](workspace.dsl). It contains:

- `SystemContext`: VitaLink users and external systems;
- `Containers`: Flutter client, Express API, MongoDB, Redis/BullMQ, and the deployment edge;
- `BackendComponents`: the principal backend components;
- `AuthComponents`, `ClinicalComponents`, and `NotificationComponents`: focused component views;
- `ProductionDeployment`: the checked-in EC2/Docker blue-green topology, explicitly tagged as repository-defined rather than live-verified.

The DSL is the architecture source of truth and is validated with the Structurizr CLI. The following prose is a readable projection, not a second model.

## System context

Patients, doctors, and administrators use the VitaLink client. The system calls external Twilio Verify, Firebase Cloud Messaging, Filebase-compatible S3 storage, a configurable payment provider, a configurable malware scanner, and optional Loki. MongoDB hosting and Redis are infrastructure dependencies inside the application runtime boundary in the container view.

## Container responsibilities

| Container | Responsibility | Primary protocol |
| --- | --- | --- |
| Flutter client | Web/mobile UI, session storage, role navigation, REST/SSE and push integration | HTTPS JSON, SSE, FCM |
| Nginx edge | Reverse proxy, edge request limiting, forwarded headers, SSE buffering/timeouts | HTTP in checked-in active config; HTTPS block is commented |
| Express API | Business logic, authentication, authorization, validation, orchestration, schedulers and workers | HTTP/JSON, SSE |
| MongoDB | Operational source of truth and durable outbox | MongoDB driver |
| Redis/BullMQ | Shared counters, stream-ticket state, pub/sub and work queue | Redis protocol |

## Important boundary note

The repository does not prove which deployment is live. The EC2/Docker model is the complete checked-in backend deployment design, while Flutter defaults and Vercel rewrites point at a Render host and another workflow publishes Flutter web to GitHub Pages. These are recorded as deployment drift in [Inconsistencies](../reference/inconsistencies.md).
